HERMES / DEVFLOW
ENGINEERING SYSTEM NOTE · 2026-11-15

Multi-agent engineering · closed-loop delivery

多代理人協作，從需求到可驗收的部署。

七個 Bot 共用一份任務依賴圖。以可觀察的驗收條件驅動實作，把 PR、獨立審查、CI 與部署證據接回同一個交付閉環。

The completion condition

完成不是「代理人說做完」。

每條 AC 都要有結果與證據。部署成功不等於驗收通過；缺漏回到任務圖，不靠聊天記憶維持進度。

對象：工程師／平台維運依據：此 repo 的 devflow 文件、角色設定與 CI/CD 範本設計說明，非線上運行狀態

01

協作閉環：人給目標，任務圖保存進度

圖中連線表示工作交接，不代表 Bot 之間直接呼叫。每個 repo 一個 Kanban board；dispatcher 依 parent 依賴派工，EPIC 等待子卡完成後再驗收。

派工語意：可獨立合併的工作才能並行；同檔寫入先拆責任。若後一張 DEV 需要前一張 PR 的程式碼，依賴前一張 [SHIP]，不是只等 DEV 寫完。七個 profile 共用原生工具，並非七套獨立排程系統。

02

交付路徑：同一套 journeys，部署前後各驗一次

以下是具備 Dockerfile、啟用部署且已接入 devflow 契約的服務路徑。PR 驗證環境與 VM 正式執行環境分開；不是把 CI 建出的同一份映像直接晉升。

03

協作靠契約，不靠共享聊天記憶

任務與工作空間

單位：一張 DEV，一個可獨立合併的 PR
卡片 body 保存目標、編號 AC、提示與「覆蓋：AC-n」。純研究或文件工作不必建立 SHIP；OPS 負責 repo 接入、CI/CD 與 runner。
隔離：工作空間不同，並行不等於可同寫
[DEV] / [OPS] 由 dispatcher 配置 worktree；[RES] / [ADV] 用 scratch；[ARCH] / [SHIP] / [EPIC] / [ADJ] 用 dir。Reviewer 在原 worktree 驗證，但不提交或改寫 PR。
等待：依賴驅動，不讓 worker 睡著輪詢
EPIC 以 dependency block 等待葉節點。預設 dispatcher 設定同時最多 4 張 in-progress、每個 profile 最多 2 張；這是派工設定，不是實際吞吐量。
調整：受限操作交給 gateway
worker 可用原生 kanban_* 工具；edit／archive／resume 等操作寫成 devflow-ops 留言，由 gateway 的 tick 執行，結果留回同一卡。

證據追溯鍵

至少能從一條 AC 找到負責卡、PR head、CI／部署 run，以及 journey 輸出或 UI 截圖。下面是跨階段關聯欄位，不是所有角色共用的單一 JSON schema。

EPIC.body
  AC-1..n                 可觀察結果

DEV / REVIEW metadata
  pr_url · head_sha       變更版本
  tests · acceptance      測試與逐條證據
  probes                  reviewer 獨立探測

SHIP metadata
  deploy_run_id           部署 run
  acceptance · followups  部署後驗證與缺漏

EPIC completion metadata
  prs · deploy_runs
  acceptance[]
    ac · verdict · probability · evidence

.devflow/evidence/AC-n.txt 保存 journey 輸出；UI journeys 保存截圖。head_sha 指 PR 版本，部署 run 的 SHA 可能是合併提交，不能假設兩者相等。

04

閉環的重點：失敗回到哪裡，恢復靠什麼證據

下表補充主圖未展開的失敗分支；回滾成功也不會把失敗的交付判為成功。
觀察到的失敗回路與責任人再次前進的條件
需求或計畫有疑慮計畫變動觸發 check plan；新疑慮交 Hermes 的 [ADV]。需要修正時，orchestrator 用 [ADJ] 調整卡片與依賴。重新建立可觀察的 AC 覆蓋。只有含不可回復操作的 ADV 會阻擋 SHIP；一般建議不擋。
PR CI 失敗／審查退件Developer 修正同一卡／PR，補足行為實作與 journeys；Reviewer 依最新 head 重審，不能拿舊 SHA 的證據放行。目前 head 的必要檢查通過，退件理由已解決；reviewer 的探測與驗收證據充分。
候選服務 up／health／verify 失敗deploy.sh 先以 capture.sh 保存候選容器的狀態、退出原因與本次部署後的 log（已遮罩），再以上一個 :live 映像 --no-build 恢復並重跑 health；本次部署仍以非零結束。build 失敗則不動執行中版本。DevOps 讀 devflow-diagnostics-deploy-<sha> 分類問題；程式問題由 developer 用 GitHub-hosted repro.yml 重現後修正並重新部署，不能以回滾健康代替 AC 驗收。
部署完成，但 AC 不完整Orchestrator 用 check acceptance 下載 run artifacts、逐條判讀。缺實作或缺 journey 就補 DEV／OPS 卡，重新掛到 EPIC。所有 AC 有 PASS 與可追溯證據。若自動判讀偏嚴，orchestrator 可附具體證據與理由判 PASS。
worker crash／卡片無法續跑Hermes 轉 ADJ；orchestrator 修根因，以 devflow-ops resume 續跑；無法修改的卡片契約則建替代卡並移接依賴。修復的設定或行為已實測。重複根因應落到 repo 的驗證／CI；kit 層問題列 followups，交使用者決定。
方向、成本或破壞性資料操作未決標記 needs_input，由 Hermes 問使用者；不是由代理人自行猜測授權。使用者決定後才續跑受影響路徑；既有未受阻工作可繼續。

目前閉環止於部署後驗收，不等於持續營運監控

repo 範本沒有定義持續 metrics／traces／SLO 監控、自動從正式環境事件開卡，或 pager 輪值。日後發現問題可再由 Hermes 建新 EPIC，但不能把這條人工入口描述成已自動化的 production feedback。

05

哪些是真的閘門，哪些仍是流程約定

控制面目前機制限制／例外
合併／卡片完成repo protect 建立 devflow ruleset，以 devflow-ci 與 devflow-judgment 為 required check，不允許 bypass；PR completion contract 核對 exact head。devops 只用 devflow ship merge 合併：當場判斷 PR 目前的 head + 說明，API 失敗、沒有 advisor ok、判斷後 PR 被改都拒絕，通過才寫入 devflow-judgment 並以 --match-head-commit 合併。需要成功接入並設置 contract。devflow-judgment 用 builder token 寫入，agent 拿得到，所以擋得住漏做檢查，擋不住刻意偽造。獨立 reviewer 是角色流程要求，不代表所有 repo 都有平台強制的 required approval。
計畫與 AC 判讀規則加 Decisions API 檢查；變動才重新檢查，重複疑慮不重複建 ADV。逐條驗收由 orchestrator 對證據負責。檢查工具出錯只記錄、不擋流程；模型判讀不是數學保證。程式碼中的失敗回傳與 GitHub required checks 才是相應的執行閘門。
驗收涵蓋範圍repo 專屬 verify.sh 必須由 developer 補入每條 AC journey；PR 與部署後共用，UI 用 Playwright。範本預設只有 health。沒有 Dockerfile 的 PR 會略過 up／verify；沒有 AC journeys 就沒有完整使用者行為證據，CI 綠也不能補足。
規則與教訓CI check job（在 devflow-ci 的 needs）：每條規則先用自帶的錯誤範例自測，再掃描程式；豁免必須引用存在的教訓，教訓的 ref 必須指到真實的規則或檔案。PR 上：fix:／revert: PR 必須帶 Lesson: 或 No-lesson:；同一根因再出現要更新原教訓；新教訓的規則或測試必須在修正前的程式上失敗，log 印出每筆證明。Hermes 主機另外判斷 PR：改到 gate 檔案一律送 advisor；Decisions 判斷修 bug 沒標 fix:、No-lesson／No-proof 理由不成立、教訓沒對準這次的錯，標出就送 advisor 並擋合併。規則是逐行模式比對，不是語意分析；journey 教訓不做自動證明，只由 Decisions 與 advisor 判斷。CI 跑的是 PR 自己的檢查程式，所以放寬檢查要靠主機的 gate 檔案偵測與 advisor 擋。模型判斷只負責送 advisor，不負責放行。agent 帳號與人的帳號未分開前，無法做成只有人能核准的權限關卡。
執行身分／網路builder 與 reviewer 使用不同 GitHub 帳號；部署在主機 devflow 使用者的 rootless Docker，服務綁 127.0.0.1。不是完整的權限隔離證明：兩帳號都有 push 權限，developer 的 git／gh 原生升權自動核准。任何有 push 權限的帳號都能在分支上寫 workflow 跑在 self-hosted runner，等同主機 devflow 使用者與共用 Docker 的權限；workflow 內的條件只防誤用。對外 proxy、TLS、DNS 不在範本契約內。
回滾與資料成功部署標記 :live，up、health 或 verify 失敗時先採證，再用它恢復應用映像。沒有上一版就無法回滾。回滾只重驗 health，不還原資料庫、volume、schema 或環境設定。診斷 log 的遮罩是盡力而為，artifact 保留 7 天。
供應鏈／發布PR 與 VM 使用相同 compose 契約；CI quality 工具在 GitHub-hosted runner，以唯讀 token 與固定 commit 執行。VM 會重新 build，尚非 build-once／promote-by-digest；也未定義映像簽章、來源證明、漸進發布或停機時間保證。
工程師接入一個 repo 時，要確認什麼？
  • 建立 repo／board、接入契約與 runner；新專案先有可啟動骨架，既有 repo 先比對 devflow contract 列出的差異。
  • 替換範本的 test、啟動與 health 設定；為每條 AC 編寫真實 journeys。不要只保留預設 health 就宣稱行為驗收完成。
  • 確認 required checks、completion contract、兩個 GitHub 身分與部署環境設定；不需要部署的專案明確選擇不走服務部署路徑。
  • 先走一個真實小變更，檢查 PR／部署兩份 artifact，再確認失敗時的回復與人工處理方式。這份 HTML 不會執行任何接入或部署命令。
模型與技能為什麼沒有放進主圖？

角色責任與交付契約比模型名稱穩定。目前 roles.json 指定 developer 使用 Codex app-server 的 gpt-6.1-sol（推理強度 high）；reviewer／Advisor 使用 claude-opus-5.5，reviewer 有 Codex fallback。實際可用性取決於 provider、登入帳號與 Codex 版本。技能分配請以角色表為準，模型切換不改變 AC 與證據責任。
